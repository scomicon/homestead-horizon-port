# Лаг при листании предметов в креативе: разбор по исходникам

Дата: 2026-11-16. Разбор только по исходникам клиента Horizon (`work/horizon-source/horizon-5f7cadf…/crates/horizon-client`), без сборки и запуска игры. **Лаг не измерен**, ниже гипотеза, подтверждённая чтением кода, и способ её проверить.

Жалоба: при пролистывании предметов в больших вкладках модов (Mcwholidays, Regions Unexplored, Create Palettes и др.) игра начинает лагать. Размеры: у `mcwholidays` 308 блоков и 335 моделей предметов, у create palettes 368 записей.

## Как устроен экран

| Что | Где | Как работает |
| --- | --- | --- |
| Сетка предметов | `game/creative_screen.rs`, `draw_creative` | Рисуется всегда ровно 5 рядов по 9 слотов (45) плюс хотбар, независимо от размера вкладки. Видимый диапазон: `first_row()`, колесо мыши двигает на одну строку (`Creative::wheel`). |
| Список вкладки | `creative.rs`, `Creative::items` | Кэшируется (`shown: Mutex<Option<Shown>>`), пересчитывается только при смене вкладки, поиска или языка. На кадр это одно сравнение и клон `Arc`. |
| «Страницы» | `creative.rs`, `pages`/`set_page`; `mod_content.rs`, `creative_tabs` | Это страницы **вкладок** (кнопки `<` `>` над экраном, по 10 вкладок мода на страницу), а не страницы предметов. Предметы листаются прокруткой. |
| Модель предмета | `game/item_draw.rs`, `draw_item_model` → `item_render::gui::draw` | Каждый кадр для каждого из 45+9 слотов: `resolve_item`, затем `gui::draw`. |
| Запечённая модель | `item_render.rs`, `ItemRenderer::bake` | Кэш `baked: Mutex<HashMap<String, Arc<BakedItemModel>>>` по имени модели. |
| Готовые вершины | `item_render/gui.rs`, `draw` + `DrawnKey` | Кэш `gui_drawn`: вершины статичного предмета в **той же позиции** (x, y); сбрасывается целиком при 8192 записях. |
| Маски спрайтов | `item_render.rs`, `FileSprites::mask`/`load` | Кэш `cache` по имени спрайта; при промахе читает PNG и `.png.mcmeta` с диска, декодирует, строит маску прозрачности по каждому уникальному кадру анимации. |

## Гипотеза: холодная запечка моделей на потоке отрисовки

**Что подтверждено кодом.**

1. Первый показ предмета в сетке вызывает `ItemRenderer::bake` (`item_render.rs:832`). Он зовёт `bake_item_model` → `bake_resolved` (`horizon-assets/src/item_bake.rs:118`), которая для каждого материала модели вызывает `sprites.mask(sprite)` (строка 122, и ещё раз в цикле слоёв). Для плоского предмета затем идёт `extrude_layer` по маске: по квадрату на каждый пиксельный край.
2. `FileSprites::load` (`item_render.rs`, около строки 600) на промахе кэша делает `hud::decode(path)` → `prepared_files::read(path)` (`horizon-client-render/src/hud.rs:155`), потом читает `.png.mcmeta` и, для анимированных спрайтов, разбирает его и строит маску по каждому уникальному кадру.
3. Один общий файл данных (`horizon-data.bin`) создаётся только для корня ванильных ресурсов (`game/resource_load.rs:528`, `write_prepared_files(vanilla_root)`). Корень с контентом модов (`mod_content.rs`, `Overlay`, строка 2195) намеренно не получает копию этого файла («он описывает основу, не этот корень»). Поэтому чтение текстур мода идёт по файлу на спрайт через `fs::read`, а отсутствующие `.mcmeta` проверяются обращением к диску. Комментарий в `prepared_files::write_with_readers` прямо признаёт, что антивирус задерживает первое открытие каждого файла. Разработчики Horizon ради этого и сделали единый файл, но для нашего корня он не работает.
4. Всё это выполняется на потоке окна, внутри `draw_creative` → `draw_item` (`item_draw.rs:390`, `resolve_item`): отдельного потока и бюджета времени нет.
5. После первого показа модель лежит в `baked`, маска в `cache`, и повторная прокрутка той же вкладки дешёвая. Исключение: кэш `gui_drawn` привязан к позиции, поэтому предмет, который сдвинулся на другой ряд, ещё раз проходит `draw_now` (сортировка и обрезка квадратов), но это уже без диска.

**Следствие, которое можно проверить.** Первая прокрутка вкладки с сотнями ещё не показанных моделей рывками, вторая проходит плавно (пока не очищен `gui_drawn`). Блоки с несколькими текстурами (мебель, настенные таблички, плюши) стоят дороже плоских предметов: на каждую текстуру приходится отдельное чтение и декодирование.

**Размер вкладки сам по себе не стоит ничего**: сетка всегда 45 слотов. Важно число различных ещё не запечённых моделей и спрайтов, которые игрок листает.

## Что исключено (проверено чтением)

- Пересоздание списка на кадр: нет, `Creative::items` кэширует.
- Подсказки с `tabs_containing` (проход по всем вкладкам с `same_components` на каждой): для обычной вкладки мода ранний выход (`tooltip_lists_tabs(category=true, grid=true)` даёт `false`, `creative_screen.rs:59`). Этот проход есть только на вкладке поиска и в инвентаре.
- Хуки `native_item_bar` и `native_item_decorations` вызываются на каждый слот каждый кадр, но ни один наш миксин (`mixins/create`, `mixins/homestead`) их не использует (поиск по `item_bar|item_decorations` в `create-source` пуст).
- Перерисовка атласов при смене страницы: не нашёл. `set_page` меняет `page` и выбирает первую вкладку (`select` → сброс прокрутки), атласы не пересобираются.

## Вторичные находки (не причина лага при прокрутке, но стоит знать)

1. **Первый поиск на не английском языке.** `search_results` при языке не English строит `localized_lines`: для каждого из всех предметов вкладки поиска (с модами это тысячи) собирает подсказку через `item_tooltip::lines` (`creative.rs:571`). Это разовый затык при первом символе в поиске, потом кэш по языку. На английском берутся готовые строки из экспорта, но у модов `lines` содержит только название (`mod_content.rs`, `creative_tabs`), так что поиск по тексту подсказки у них не работает.
2. **`tab_headers()` на каждый кадр** клонирует `id`, `title`, `icon` всех вкладок (`creative_screen.rs:87`): три строки на вкладку, при 100+ вкладках сотни мелких выделений в кадр. Мелочь, но бесплатно исправляется (передавать ссылки).
3. **`click_creative` клонирует `creative_screen.tabs` целиком, вместе со всеми стеками** на каждый клик мыши по экрану (`creative_screen.rs`, строка с `tabs.clone()`). Лаг на клике, не на прокрутке.
4. **`creative_tabs` в `mod_content.rs`**: `known(id)` проверяет `new.contains(&id)` линейным проходом по всем новым предметам, для каждого предмета каждой вкладки. Квадратичная сложность при сборке списка (один раз при подготовке ресурсов, не в кадре).
5. **`DRAWN_LIMIT = 8192`** записей `gui_drawn`: при позиционном ключе (45 позиций сетки × число предметов) длинная прокрутка по нескольким большим вкладкам упрётся в предел и очистит кэш целиком. После этого повторные показы дороже, но без диска.

## Предложения

### A. Разогрев моделей сетки (патч движка, предложен, не применён)

Файл `stage4/engine-patches-proposed/24-creative-warm.ps1`. Каждый кадр, пока открыта вкладка мода, `warm_creative_rows` вызывает `resolve_item` для ещё не показанных стеков вкладки, начиная с видимых рядов и по кругу, не дольше 3 мс за кадр. Результат отбрасывается, остаются заполненные кэши `baked` и `cache`. Новых полей и файлов нет, картинка не меняется. Прогресс хранится в `thread_local` и сбрасывается при смене списка (адрес и длина).

- Лежит **вне** `engine-patches/`: `build.ps1` применяет все `*.ps1` из той папки. Чтобы включить, перенести файл в `engine-patches/` и пересобрать (`build.ps1`, затем `Prepare-Candidate.ps1`).
- Проверено: патч применяется к копии `creative_screen.rs` из исходников, повторный запуск ничего не меняет (идемпотентен), результат проходит `rustfmt --check`. **Компиляция не проверялась**: в `draw_creative` ссылка на `items` и вызов `&self`-метода должны ужиться с `&mut self`, `player_owner` и `resolve_item` видны из соседнего модуля `game` (оба `pub(super)`), `DisplayContext` указан полным путём.
- Ограничение: на 3 мс/кадр разогревается около 3 холодных моделей за кадр (если одна стоит ~1 мс), то есть ~300 моделей за 1.5-2 секунды после открытия вкладки. Если игрок листает быстрее, часть затыка остаётся. Если 3 мс заметно просаживают кадр, уменьшить бюджет.

### B. Данные: разбивка вкладок по 45 предметов не поможет с лагом

Сетка всё равно рисует 45 слотов, а стоимость в числе различных холодных моделей. Разбивка не сократит число текстур, которые нужно прочитать, и добавит страницы вкладок (по 10 на страницу). Для навигации она может быть удобна, но **не как исправление лага**. То же с ограничением числа слотов.

Что в данных действительно помогает:
- Не класть в вкладку настенные и служебные варианты без иконки (отдельная задача: аудит вкладок, пустые слоты тоже холодные запросы с запасной моделью).
- Давать предметам одну общую текстуру там, где это допустимо (мебель одного набора): меньше чтений.

### C. Мелкие правки экрана (позже, отдельным патчем)

Пункты 2 и 3 вторичных находок (`tab_headers` на кадр, клон вкладок на клик) лежат в `game/creative_screen.rs`, который мы меняем только патчем движка. Делать их стоит, лишь если замеры покажут, что они заметны; в этом разборе они не приоритет.

### D. Файл данных для корня модов (потенциально самое сильное, но дорогое)

Если `prepared_files::write` научить собирать `horizon-data.bin` и для корня с контентом модов (`mod_content.rs` его нынешней схемой исключает), то чтение текстур мода станет чтением из одного файла, как у ванильного корня, а отсутствующие `.mcmeta` перестанут обращаться к диску. Это изменение схемы упаковки в движке Horizon, оно затрагивает инвалидацию кэша при смене набора модов. Предлагается как запрос к разработчикам Horizon (в `research/horizon-hook-requests.md` не заносилось), а не как наш патч.

**Не проверено**
- Сам лаг не измерен, ни профилировщиком, ни по кадрам. Гипотеза «первая прокрутка рывками, вторая плавная» не проверена в игре.
- Не проверено, что корень мода действительно без `horizon-data.bin` в рабочей установке (вывод из кода: `write_prepared_files` вызывается только для ванильного корня, `resource_load.rs:528`).
- Патч A не компилировался.
- Не проверено, не добавляет ли антивирус заметной задержки на этой машине.

**Как проверить**
1. Открыть вкладку Mcwholidays, прокрутить колесом от начала до конца, затем обратно, затем ещё раз. Если первый проход рваный, а второй и третий плавные, гипотеза верна.
2. Повторить после включения патча A: рывков при первой прокрутке должно стать заметно меньше, если подождать 2-3 секунды после открытия вкладки.
3. Если лагает и второй проход, причина другая (кандидаты: `gui_drawn`, очищаемый на 8192 записях; `draw_now` для блочных моделей с большим числом квадратов), нужен профиль кадра.
